# Дневник смен водителя

Мини-приложение: FastAPI + PostgreSQL (миграции Alembic) и клиент на чистом JS. Показывает сводку за день (поездки, выручка, комиссия, «на руки», наличные/карта) и список поездок; дни переключаются стрелками или выбором даты. Новые поездки добавляются через API с проверкой данных и защитой от дублей.

## Что сделано

- API: поездки за день, сводка за день, список дней с данными, добавление поездки.
- Проверка данных: сумма > 0, окончание позже начала, 0 ≤ комиссия ≤ сумма, оплата `cash`/`card`, время с часовым поясом.
- Защита от дублей: повторная отправка той же поездки не создаёт запись.
- Клиент: одна страница, сводка и список поездок, переключение дней.
- Миграции Alembic, загрузка данных из `data/trips.json`, Docker Compose.
- 13 тестов: расчёт сводки, дубли, валидация, границы дня около полуночи.

## Запуск

Нужен Docker.

```bash
docker compose up --build
```

Приложение: http://localhost:8000 · Swagger: http://localhost:8000/docs

При старте применяются миграции и загружаются тестовые данные из `data/trips.json` (10 поездок за 3 дня). Загрузка идемпотентна: повторный запуск дублей не создаёт. Остановка: `Ctrl+C`, затем `docker compose down`.

### Без Docker (SQLite, для быстрого просмотра)

Нужен Python 3.10+.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
export DATABASE_URL=sqlite:///diary.db   # PowerShell: $env:DATABASE_URL = "sqlite:///diary.db"
alembic upgrade head && python -m app.seed
uvicorn app.main:app
```

Настройки через переменные окружения: `DATABASE_URL` (по умолчанию PostgreSQL из compose-файла) и `APP_TZ` (по умолчанию `Asia/Almaty`).

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/trips?date=YYYY-MM-DD` | поездки за день |
| GET | `/api/summary?date=YYYY-MM-DD` | сводка за день |
| GET | `/api/days` | дни, в которых есть поездки (клиент открывает последний) |
| POST | `/api/trips` | добавить поездку |

Ответы на `POST /api/trips`: `201` — создана, `200` — такая поездка уже есть, `409` — тот же `id` с другими данными, `422` — данные не прошли проверку.

```bash
curl -X POST localhost:8000/api/trips -H 'content-type: application/json' \
  -d '{"id":"t11","start":"2026-10-03T08:00:00+05:00","end":"2026-10-03T08:20:00+05:00","amount":2000,"payment":"cash","commission":300}'
```

## Принятые решения

- **День** — календарный день в `APP_TZ`. Поездка относится ко дню начала, поэтому ночная поездка через полночь не раздваивается. Время в API отдаётся в `APP_TZ`, клиент показывает его как есть.
- **Дубли.** `id` — первичный ключ и ключ идемпотентности. Повтор ловится ограничением БД, а не проверкой «сначала select, потом insert», поэтому защита работает и при двух одновременных запросах.
- **Валидация** выполняется в API; те же условия продублированы CHECK-ограничением в БД.
- **Деньги** — целые числа (как в примере), без float. «На руки» = выручка − комиссия.
- **Не сделано:** формы добавления поездки в клиенте нет, добавление через API или Swagger.

## Как использовался ИИ

Задачу, стек (FastAPI, Alembic, PostgreSQL) и требования задавал я. Архитектуру, код, миграцию, тесты, тестовые данные и первую версию этого README написал Claude (Anthropic) в одном диалоге. Результат я запускал и проверял.

**Что поручено ИИ:** схема БД и миграция, API, проверка данных, защита от дублей, тесты, клиент.

**Что ИИ сделал осознанно:**
- границы дня считаются в часовом поясе водителя, а не в UTC, чтобы поездка в 00:20 не попадала в предыдущий день (есть тест);
- дубли ловит первичный ключ в БД, а не проверка перед вставкой;
- деньги хранятся целыми числами, без float.

**Где ИИ ошибся:**
- при создании структуры проекта он использовал bash-синтаксис `{a,b}` в оболочке, которая его не поддерживает: папки создались неправильно, файлы не записались, структуру пришлось пересоздавать;
- он не мог запустить PostgreSQL и Docker, поэтому тесты, миграцию и загрузку данных проверял только на SQLite.

**Что проверил я сам:** запуск через `docker compose` с PostgreSQL, тесты, сценарий с повторной отправкой одной и той же поездки (201, затем 200, затем 409 при изменённых данных).
